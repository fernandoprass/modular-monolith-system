# Core E2E Tests

E2E means end-to-end.

An E2E test checks a real user flow through the API.

It does not call only one service.

It starts the API host, sends HTTP requests, uses a real database, and verifies the final result.

E2E tests are important because they catch integration problems.

They can find issues in:
- routing
- authentication
- authorization
- database mappings
- migrations
- seed data
- Redis cache behavior
- service orchestration
- JSON request and response contracts

Unit tests are still faster and better for small rules.

E2E tests are better for complete business flows.

---

## Why They Are In Core

The E2E tests live in:

```text
tests/00.Core/Core.API.EndToEnd.Tests
```

They test the Core API host.

Core API loads all module controllers in one modular monolith process.

That means one E2E test can call real IAM endpoints through the same host used by local Core mode.

This is useful because:
- Core API is the production-like modular monolith entry point.
- Authentication and authorization run as real middleware.
- Module controllers are loaded through Application Parts.
- Shared infrastructure, IAM infrastructure, Redis, and PostgreSQL are wired together.
- Future module flows can be tested across modules from the same project.

The tests are not inside IAM because the goal is not only to test IAM services. Also, new modules can be added without needing to create a new E2E test project.

The goal is to test the API flow through the real Core host.

---

## Architecture

The test project has two main folders:

```text
tests/00.Core/Core.API.EndToEnd.Tests
+-- Infrastructure
+-- Scenarios
```

`Infrastructure` contains reusable test building blocks.

`Scenarios` contains business flows.

---

## Test Fixture

The main fixture is:

```text
Infrastructure/CoreApiTestFixture.cs
```

It inherits from `WebApplicationFactory<Program>`.

It starts the Core API in memory for tests.

It also starts real infrastructure with Testcontainers:
- PostgreSQL
- Redis

The fixture configures the test host with:
- IAM database connection string
- Shared database connection string
- Redis connection string
- JWT secret
- internal API key
- hosted services disabled

Hosted services are disabled because E2E tests should focus on request/response flows.

Example disabled services:
- audit log consumers
- system log consumers
- email workers
- index initializers

This keeps tests more stable.

---

## Database Setup

The fixture runs migrations before the scenarios.

It migrates:
- Shared database context
- IAM database context

Then it seeds the minimum data needed by the tests.

Seed data includes:
- IAM permissions
- default roles
- role permissions
- security parameters
- default role parameters

The fixture also has small ensure methods.

These methods make the seed safer when the database already has partial data.

Examples:
- `EnsureRoleDeletePermissionAsync`
- `EnsureDefaultUserPermissionsAsync`

This avoids fragile tests when seed data changes.

## API Clients

The tests do not repeat raw `HttpClient` calls inside each scenario.

They use reusable API client classes.

### CoreApiClient

File:

```text
Infrastructure/CoreApiClient.cs
```

This client is used before login.

It supports public operations:
- create organization
- login

Login returns an authenticated client.

### AuthenticatedCoreApiClient

File:

```text
Infrastructure/AuthenticatedCoreApiClient.cs
```

This client wraps authenticated API calls.

It stores the JWT token returned by login.

Each request adds:

```text
Authorization: Bearer {token}
```

It contains reusable methods for:
- organization operations
- user operations
- role operations
- permission operations
- parameter operations
- authorization checks

Examples:
- `GetOrganizationAsync`
- `UpdateOrganizationAsync`
- `CreateUserAsync`
- `AssignRoleAsync`
- `AssignPermissionsAsync`
- `SearchPermissionsAsync`
- `GetParameterValueAsync`
- `CheckPermissionAsync`

These methods keep scenarios readable.

They also keep endpoint paths in one place.

---

## Response Helpers

File:

```text
Infrastructure/HttpResponseMessageExtensions.cs
```

This file contains helpers for HTTP responses.

Important helpers:
- `EnsureSuccessStatusCodeAsync`
- `ReadResultDataAsync<T>`

`EnsureSuccessStatusCodeAsync` throws a useful error when the HTTP status is not successful.

`ReadResultDataAsync<T>` reads the API response wrapper and returns only the `Data` value.

This keeps scenario code clean.

---

## Test Data Factory

File:

```text
Infrastructure/ScenarioDataFactory.cs
```

This factory creates valid requests for scenarios.

Examples:
- organization creation
- organization update
- user creation
- user update
- password update
- role creation
- role update

It generates unique names, codes, and emails.

That avoids conflicts when tests run together.

---

## Scenario Style

Scenario tests should read like a user flow.

Good pattern:

```text
Arrange request data
Create organization
Login
Call business endpoints
Read final state
Cleanup created data
Assert final state
```

Keep reusable mechanics in infrastructure.

Keep business intent in scenarios.

Do not duplicate login code.

Do not duplicate raw endpoint paths in scenario files.

Add a new method to `AuthenticatedCoreApiClient` when a scenario needs a new authenticated API call.

Add a new factory method to `ScenarioDataFactory` when a scenario needs reusable request data.

## When To Add New E2E Tests

Add an E2E test when the flow depends on multiple pieces working together.

Good candidates:
- login and authorization
- role and permission changes
- parameter override behavior
- workflows that use more than one endpoint
- flows that depend on seeded data
- flows that depend on middleware

Do not add E2E tests for every small validation rule.

Use unit tests for small service and domain rules.

Use E2E tests for important happy paths and high-risk integration paths.
