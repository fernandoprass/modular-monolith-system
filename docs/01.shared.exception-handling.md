# Shared Exception Handling

This document explains how API exceptions are handled.

The shared exception handling code lives in:

```text
back/src/01.Shared/Shared.Infrastructure/ExceptionHandling
```

The goal is simple:
- return the same API error shape in every module.
- log unhandled exceptions as system logs.
- keep module API handlers small.
- avoid logging sensitive request data.

---

## Main Flow

When an unhandled exception reaches an API:

```text
GlobalExceptionHandler
  -> ExceptionResponseWriter
    -> ExceptionResponseFactory
  -> ExceptionSystemLogPublisher
    -> SystemLogEventFactory
      -> ExceptionRequestFactory
      -> ExceptionRetentionPolicyResolver
    -> IEventPublisher
      -> Sentinel persists the system log
```

Sentinel is different.

Sentinel can persist exception logs directly.

This avoids losing Sentinel errors when Redis is unavailable.

---

## Shared Responsibilities

Shared owns reusable exception behavior.

| Class | Responsibility |
| :--- | :--- |
| `ExceptionResponseFactory` | Maps an exception to HTTP status, public message, and details. |
| `ExceptionResponseWriter` | Writes the JSON API response. |
| `ExceptionRequestFactory` | Builds safe request metadata for system logs. |
| `ExceptionRetentionPolicyResolver` | Chooses the retention policy for the system log. |
| `SystemLogEventFactory` | Creates the `SystemLogEvent`. |
| `ExceptionSystemLogPublisher` | Publishes the `SystemLogEvent`. |

Shared should not know IAM, Courier, or Sentinel business rules.

Shared only receives the module name from the module API.

---

## Module API Responsibilities

Each module API keeps only module-specific wiring.

The IAM handler is a good example:

```csharp
public async ValueTask<bool> TryHandleAsync(
    HttpContext httpContext,
    Exception exception,
    CancellationToken cancellationToken)
{
   _logger.LogError(exception, "An unhandled exception occurred: {Message}", exception.Message);

   await ExceptionResponseWriter.WriteAsync(httpContext, exception, cancellationToken);
   await PublishSystemLogAsync(httpContext, exception, cancellationToken);

   return true;
}
```

The module API should:
- log the exception locally.
- call `ExceptionResponseWriter.WriteAsync`.
- pass the module name when publishing the system log.
- protect logging failure with a `try/catch`.

Example from IAM:

```csharp
await publisher.PublishAsync(
   IamConst.System.ModuleName,
   httpContext,
   exception,
   cancellationToken);
```

The module API should not:
- duplicate exception response mapping.
- build system log events by hand.
- decide retention policy.
- log request bodies.

## API Response

`ExceptionResponseFactory` maps known exception types to HTTP responses.

Current mappings:

| Exception | Status Code | Public Message |
| :--- | :--- | :--- |
| `OperationCanceledException` | `408` | The request was canceled. |
| `TimeoutException` | `504` | The request timed out. |
| `KeyNotFoundException` | `404` | The requested resource was not found. |
| `ArgumentException` | `400` | The request is invalid. |
| `NotImplementedException` | `501` | This feature is not implemented. |
| `DbUpdateException` | `400` | A database error occurred. |
| `UnauthorizedAccessException` | `401` | Unauthorized access. |
| any other exception | `500` | An unexpected error occurred. |

`ExceptionResponseWriter` writes JSON with camel-case fields:

```json
{
  "message": "An unexpected error occurred.",
  "details": "Original exception message"
}
```

## System Log Event

`SystemLogEventFactory` creates a system log event from:
- module name.
- HTTP context.
- exception.
- current user context.

It sets:
- `Level` to `Error`.
- `Status` to `Unauthorized` for status code `401`.
- `Status` to `Failure` for other status codes.
- `UserId` from `IUserContext.UserId`.
- `OrganizationId` from `IUserContext.OrganizationId`.
- `RequestId` from `HttpContext.TraceIdentifier`.

Empty user or organization IDs are stored as `null`.

---

## Request Metadata

`ExceptionRequestFactory` stores safe request metadata.

It includes:
- HTTP method.
- scheme.
- host.
- path.
- query parameter names.
- content type.
- content length.
- response status code.

It does not store:
- query values.
- request body.
- authorization headers.
- cookies.

This is intentional.

Request bodies and query values can contain secrets.

---

## Retention Policy

`ExceptionRetentionPolicyResolver` decides how long to keep system logs.

Current rules:

| Exception or Status | Retention Policy | Reason |
| :--- | :--- | :--- |
| `UnauthorizedAccessException` | `Extended` | Security-related event. |
| status code `401` | `Extended` | Security-related event. |
| `DbUpdateException` | `Standard` | Data failure may need investigation. |
| `NotImplementedException` | `Standard` | Feature gap may need follow-up. |
| `TimeoutException` | `Operational` | Runtime/availability issue. |
| `TaskCanceledException` | `Operational` | Runtime/availability issue. |
| `OperationCanceledException` | `Operational` | Runtime/availability issue. |
| `KeyNotFoundException` | `Operational` | Common request failure. |
| `ArgumentException` | `Operational` | Common request failure. |
| any other exception | `Operational` | Default operational log. |

Order matters when one exception type inherits another.

Example:
- `TaskCanceledException` inherits from `OperationCanceledException`.
- Put `TaskCanceledException` first if it needs a different rule later.

---

## Adding A New Exception Type

When adding a new exception mapping:

1. Add the API response rule in `ExceptionResponseFactory`.
2. Add the retention rule in `ExceptionRetentionPolicyResolver` if needed.
3. Add focused unit tests in `Shared.Infrastructure.Tests.ExceptionHandling`.
4. Do not add module-specific rules to Shared.

Use Shared for generic exception types only.

If a module needs special behavior, keep that behavior in the module API handler.

---

## Design Rules

- Business validation should return `Result`.
- Exceptions are for unexpected failures.
- Shared owns common exception helpers.
- Module APIs own module names and handler registration.
- Do not log secrets.
- Do not log request bodies.
- Keep exception logs useful for support and operations.
