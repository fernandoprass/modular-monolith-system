# Translated Response Messages

This guide explains business messages returned by the API and displayed by the frontend.

These messages describe the outcome of an operation. They are different from Courier email templates, stored notifications, and Redis events.

## Ownership

| Component | Responsibility |
| :--- | :--- |
| `BaseTranslatedMessagesProvider` | Stores message and variable translations. Provides message factory helpers. |
| `SharedTranslatedMessagesProvider` | Owns generic message text, including CRUD success sentences. |
| Module providers, such as `IamTranslatedMessagesProvider` and `CourierTranslatedMessagesProvider` | Own module-specific messages and translated entity names. |
| Frontend API helpers | Preserve backend message text when reading responses. |
| Pages and dialogs | Display the returned text through `showSuccess`. |

Shared must not know IAM or Courier entities. For example, Shared owns the sentence `{entity} updated successfully.`, while IAM owns the translated name for User.

Provider code lives under each module's `Domain/Messages` folder. Entity translation keys live in module constants, such as `IamConst.Message.Variable.User`.

## CRUD Success Messages

CRUD means create, read, update, and delete. The shared success classes cover the three write operations:

| Provider helper | Shared class | Message code |
| :--- | :--- | :--- |
| `CreatedSuccess(entityKey)` | `CreatedSuccessInfo` | `CrudCreatedSuccessInfo` |
| `UpdatedSuccess(entityKey)` | `UpdatedSuccessInfo` | `CrudUpdatedSuccessInfo` |
| `DeletedSuccess(entityKey)` | `DeletedSuccessInfo` | `CrudDeletedSuccessInfo` |

The abstract `CrudSuccessInfo` base combines the shared sentence translations with the entity translations supplied by the module provider.

Example from an IAM update:

```csharp
return Result.Success(
   IamTranslatedMessagesProvider.Instance.UpdatedSuccess(
      IamConst.Message.Variable.User));
```

When creation also returns a DTO, include both the data and message:

```csharp
return new Result<PermissionDto>(
   permission.ToPermissionDto(),
   [IamTranslatedMessagesProvider.Instance.CreatedSuccess(
      IamConst.Message.Variable.Permission)]);
```

Courier uses the same helpers on `CourierTranslatedMessagesProvider.Instance`. No module-specific CRUD subclasses are needed.

Register entity names with `AddVariableTranslation` for English, Spanish, and Brazilian Portuguese, using `LanguageOptions` constants. Register every key before calling a CRUD helper: `GetVariableTranslations` throws when a key is missing.

## Other Business Messages

Use module-owned classes when an operation needs its own wording. IAM examples are:

- `RoleAssignedInfo` and `RoleUnassignedInfo`.
- `PermissionAssignedInfo` and `PermissionUnassignedInfo`.

These classes use translations from `IamTranslatedMessagesProvider`. They are not CRUD success subclasses.

`SuccessInfo` provides a generic success message when a more specific message is not needed. Business validation failures use error messages in `Result.Failure(...)`.

## API Response

Business responses use the Result wrapper. The frontend reads these fields:

| Field | Meaning |
| :--- | :--- |
| `data` | Returned DTO or other value; may be null for operations without data. |
| `isSuccess` | Whether the business operation succeeded. |
| `title` | Summary text, normally the first message's text. |
| `messages` | Messages with `type`, `code`, `text`, and `variables`. |

The backend owns the business wording and translations. The frontend displays the returned text rather than translating message codes or rebuilding sentences from variables.

Unhandled exceptions currently use a different response shape. See [Shared Exception Handling](01.shared.exception-handling.md#api-response).

## Frontend Flow

Shared response helpers live in `front/apps/src/data/result.ts`.

```text
API Result
  -> Resource API helper
    -> getApiSuccessText(response)
  -> Page or dialog
    -> showSuccess(message)
```

`getApiSuccessText` first validates success through `ensureResultSuccess`. A failed Result throws `ApiResultError`, even when the HTTP request succeeded.

For successful responses, it:

1. Uses a nonblank `title`.
2. Otherwise joins nonblank `messages[].text` values with newlines.
3. Returns an empty string when no text is available.

`ToastProvider` skips empty or whitespace-only messages.

Create helpers return `ApiMutationResult<TData>`, containing `data` and `message`. Update, delete, and assignment helpers return the message string.

```tsx
const { data: created, message } = await createRole(value)
showSuccess(message)
onCreated(created)
```

```tsx
const message = await assignRolePermissions(id, permissionIds)
showSuccess(message)
```

Keep Result parsing in API helpers, not pages. Continue using `en.ts` for UI labels, confirmation questions, empty states, and client-side validation. Do not duplicate backend success sentences there.

Error handling remains separate through `ApiResultError` and `getApiErrorText`. Currently, error text falls back from `title` only when it is null or undefined; the nonblank-title behavior described above applies to `getApiSuccessText`.

## Adding A Message

1. Decide whether the message is generic or module-specific.
2. For CRUD success, add the entity key and its translations to the module, then use the inherited provider helper.
3. For a module-specific operation, add its message class, code, and translations in that module.
4. Return the message in the service Result after the operation succeeds.
5. Preserve the response text in the frontend API helper and display it in the caller.
6. Check title fallback, failure responses, and responses without message text.
