# Sentinel Entities

Sentinel is the logging and monitoring module.

It stores system activity and technical errors in a centralized place.

The main Sentinel entities are:
- `AuditLog`
- `SystemLog`

Both entities live in:

```text
back/src/02.Sentinel/Sentinel.Domain/Entities
```

---

## 1. Entity Design

Sentinel logs are append-only records.

That means the normal flow is:

```text
Create log -> Save log -> Query log later
```

Logs should not be updated as normal business behavior.

Because of that, `AuditLog` and `SystemLog` inherit from `Entity`, not `EntityAudited`.

Why:
- The log already has its own `Timestamp`.
- Logs are not modified after creation.
- `CreatedAt` and `UpdatedAt` from `EntityAudited` would not add much value.

---

## 2. AuditLog Entity

`AuditLog` stores business actions.

It answers:

```text
Who did what, when, and to which target?
```

Examples:
- User updated.
- Role assigned to user.
- Permission assigned to role.
- Parameter override deleted.
- Login succeeded.
- Login failed.

### Properties

- **Id** (`Guid`): Unique identifier for the log. This uses the event ID generated by the publisher.
- **Module** (`string`): Source module, e.g. `iam` or `shared`.
- **Feature** (`string`): Functional area, e.g. `users`, `roles`, `permissions`, `parameters`.
- **Action** (`string`): Action performed, e.g. `create`, `update`, `assign`, `unassign`, `delete`.
- **PrivacyLevel** (`AuditPrivacyLevel`): Sensitivity level of the audit data.
- **Description** (`string`): Human-readable summary.
- **IpAddress** (`string?`): Request IP address when available.
- **UserAgent** (`string?`): Client user agent when available.
- **CreatedAt** (`DateTime`): UTC time when the event happened in the source module.
- **ExpiresAt** (`DateTime?`): Optional time when the log can be deleted.
- **UserId** (`Guid`): User who performed the action.
- **OrganizationId** (`Guid`): Organization/tenant context.
- **TargetId** (`Guid`): Main entity affected by the action.
- **Metadata** (`string`): Extra context stored as JSON.

### Factory

`AuditLog` is created with the static factory method.

```csharp
var auditLog = AuditLog.Create(
   auditEvent.Id,
   auditEvent.Timestamp,
   auditEvent.Module,
   auditEvent.Feature,
   auditEvent.Action,
   auditEvent.PrivacyLevel,
   auditEvent.Description,
   auditEvent.UserId,
   auditEvent.OrganizationId,
   auditEvent.TargetId,
   auditEvent.IpAddress,
   auditEvent.UserAgent,
   auditEvent.Metadata);
```

If metadata is empty, the entity stores:

```json
{}
```

### Theoretical Context

Audit logs are used for traceability and compliance.

They are business-level logs, not developer debugging logs.

They should be understandable by a support or security user.

Example:

```text
User X assigned Role Y to User Z.
```

Do not store secrets in metadata.

---

## 3. SystemLog Entity

`SystemLog` stores technical events.

It answers:

```text
What happened inside the system?
```

Examples:
- Unhandled exception.
- Background consumer processing failure.
- Database connection error.
- Unauthorized exception caught by the global handler.

### Properties

- **Id** (`Guid`): Unique identifier for the log. This uses the event ID generated by the publisher.
- **Module** (`string`): Component that generated the log, e.g. `IAM.API`.
- **Level** (`SystemLogLevel`): Severity level, e.g. Debug, Information, Warning, Error, Critical.
- **Status** (`SystemLogStatus`): Operation result, e.g. Unknown, Success, Failure, Error, Unauthorized.
- **Message** (`string`): Main log message.
- **Exception** (`string?`): Exception type or message.
- **StackTrace** (`string?`): Stack trace when available.
- **CreatedAt** (`DateTime`): UTC time when the event happened in the source module.
- **ExpiresAt** (`DateTime?`): Optional time when the log can be deleted.
- **RequestId** (`string?`): HTTP request correlation ID when available.
- **UserId** (`Guid?`): User context when available.
- **OrganizationId** (`Guid?`): Organization/tenant context when available.
- **PropertiesJson** (`string`): Extra structured data stored as JSON.

### Factory

`SystemLog` is created with the static factory method.

```csharp
var systemLog = SystemLog.Create(
   systemLogEvent.Id,
   systemLogEvent.Timestamp,
   systemLogEvent.Level,
   systemLogEvent.Status,
   systemLogEvent.Source,
   systemLogEvent.Message,
   systemLogEvent.Exception,
   systemLogEvent.StackTrace,
   systemLogEvent.RequestId,
   systemLogEvent.UserId,
   systemLogEvent.OrganizationId,
   propertiesJson);
```

If properties JSON is empty, the entity stores:

```json
{}
```

### Theoretical Context

System logs are used for debugging, monitoring, and incident investigation.

They are technical logs.

They should help a developer understand failures.

Example:

```text
IAM.API threw DbUpdateException during user update.
```

Do not use `SystemLog` for normal business activity.

Use `AuditLog` for that.

---

## 4. Event Mapping

Sentinel does not receive logs by direct method calls from other modules.

Other modules publish events to Redis.

Sentinel consumes those events and creates entities.

| Event | Entity | Consumer |
| :--- | :--- | :--- |
| `AuditLogEvent` | `AuditLog` | `AuditLogConsumer` |
| `SystemLogEvent` | `SystemLog` | `SystemLogConsumer` |

Flow:

```text
IAM / Shared
  -> Redis stream
    -> Sentinel consumer
      -> AuditLog or SystemLog
        -> PostgreSQL
```

The consumers live in:

```text
back/src/02.Sentinel/Sentinel.Infrastructure/BackgroundServices
```

---

## 5. Relationships

`AuditLog` and `SystemLog` do not have navigation properties to IAM entities.

Example:
- `AuditLog.UserId` stores the user ID.
- It does not reference `IAM.Domain.Entities.User`.

Reason:
- Sentinel must stay decoupled from IAM.
- Logs may come from many modules.
- Sentinel should store identifiers and context, not depend on source entities.

---

## 6. Query Side

Sentinel exposes read models through DTOs.

Examples:
- `AuditLogDto`
- `AuditLogLiteDto`
- `SystemLogDto`
- `SystemLogLiteDto`

Search requests:
- `AuditLogSearchRequest`
- `SystemLogSearchRequest`

Query repository:
- `ISentinelLogQueryRepository`

API responses should return DTOs.

Do not expose entities directly from controllers.

---

## 7. Design Principles

- **Append-only logs**: Create logs, then query them. Do not update them.
- **Module decoupling**: Other modules publish events. Sentinel stores logs.
- **No source entity references**: Store IDs and context instead of navigation properties.
- **JSON metadata**: Store flexible extra context without changing the table for every new detail.
- **UTC timestamps**: Use UTC for all server-side log times.
- **No secrets**: Do not store passwords, tokens, or credentials in metadata/properties.

These entities form the storage foundation for system observability.
