# Database Seeder

The database seeder creates default data.

Project:
- `src/99.Seeder/DatabaseSeeder`

It is a console application and is intentionally separated from the other modules because it is an application used only to create the basic data necessary to run the application.

---

## Why It Exists

Useing IAM module as example:
- IAM owns IAM business rules.
- IAM should not be responsible for executing startup data creation.
- The seeder is an external startup/infrastructure project.
- It consumes IAM and Shared infrastructure.
- It inserts the default data needed for a working system.

This keeps module boundaries cleaner.

---

## What It Seeds

Current IAM seed flow creates:
- Permissions.
- Roles.
- Role permissions.
- Parameters.
- Organizations.

Main orchestrator:
- `IamDatabaseSeeder`

Seeders:
- `SeederPermissions`
- `SeederRoles`
- `SeederRolePermissions`
- `SeederParameters`
- `SeederOrganizations`

Support:
- `SeederUserContext`

---

## Seed Order

Order matters.

Current order:

1. Permissions.
2. Roles.
3. Role permissions.
4. Parameters.
5. Organizations.

Why:
- Role permissions need roles and permissions.
- Organizations may need roles.
- Parameters are independent but must exist before runtime reads.

---

## Data Access Rule

Seeders should use:
- DbContext when simple and local to Shared setup.
- Repositories.
- Unit of Work.

Seeders should not use application services.

Reason:
- Services contain runtime behavior.
- Services may validate rules that are not needed for seed data.
- Services may publish audit logs.
- Services may depend on current request context.

Seeder validation should usually be:

```text
Does this record already exist?
```

If yes, skip it.

If no, create it.

---

## Idempotency

Seeders must be idempotent.

Running the seeder twice must not create duplicates.

Use natural unique values to check existence.

Examples:
- Permission code.
- Role name.
- Parameter key.
- Organization code.

---

## Connection String

The seeder reads the connection string from:

```text
ConnectionStrings__IamDb
```

Fallback:

```text
IAM_DB_CONNECTION
```

Local fallback:

```text
Host=127.0.0.1;Port=5432;Database=iam;Username=admin;Password=cmsadmin123
```

The schema must already exist.

Run migrations first.

- `SharedDbContext`
- `IUserContext`

This gives audit fields a stable system context.

```text
DatabaseSeeder
```

---

## Adding New Seed Data

When adding new permission data:

1. Add permission constants.
2. Add permission seeder entry.
3. Add role-permission seeder entry.
4. Keep codes lowercase.
5. Ensure the seeder checks for existing data.

When adding new parameters:

1. Add parameter seed entry.
2. Use stable parameter key.
3. Do not duplicate existing keys.

---

## Rules

- Keep seed execution outside IAM.
- Keep seeders idempotent.
- Use repositories and unit of work.
- Do not use application services.
- Do not publish audit logs for seeder actions unless explicitly required.
- Do not call controllers.
- Do not create schema here.
- Run migrations before seeding.
